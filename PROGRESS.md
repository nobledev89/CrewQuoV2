> **Library deviation:** the plan named `jspdf`/`xlsx`; this ships `jspdf@4` + **`exceljs@4`**. SheetJS's public-npm `xlsx@0.18.5` is its last registry release and carries CVE-2023-30533 and CVE-2024-22363; current builds ship only from the vendor's own CDN, which pnpm lockfiles and CI resolve badly. `exceljs` is maintained, write-oriented and has no equivalent advisory. §2's "one server-side rendering path" is unchanged.
>
> **jsPDF encodes Latin-1, not Unicode.** An em dash, an ellipsis and an arrow are *silently dropped from the page* — no substitution, no error. > **Pre-existing bug found and fixed (Phase 3 code, outside this scope).** `transitionExpense` and `transitionSubmission` interpolated `$3` only inside `case when $3 is null`, where Postgres has no column to infer a type from and refuses to parse the statement at all: *"could not determine data type of parameter $3"*. **Every expense and project-submission transition — submit, approve, reject — had been 500ing since Phase 3**, which is why `expenseCostCents` was always 0. Time logs were unaffected (different query shape), and Phase 3's verification only exercised time logs, so nothing caught it. Fixed with an explicit `$3::uuid`; the e2e script now asserts the whole expense workflow.

> **Audit design notes.** `audit_logs.company_id` is *whose activity* it is (the actor's active company) and `visible_to_client` says whether the company that hired them may see the row — so exposure is opt-in three times over: the row's flag, the provider's `audit_visibility` feature, and that engagement's `show_audit_trail`. Descriptions never name a counterparty, so a visible row can't leak who a subcontractor is. `recordAudit` never throws: a broken trail must not fail an approval, so failures are logged instead. Starter plans retain 30 days but can't *read* the trail until Pro — that's the seed's intent (§5B), not a bug.

> **API hardening found while verifying (2026-08-17).** No route validated that an `:id` path parameter was a UUID, and nothing mapped Postgres error codes — so `GET /v1/projects/not-a-uuid` reached a `uuid` column, raised SQLSTATE `22P02`, and came back as **`500 Internal server error`**. That was true of *every* `:id` route in the app, and it is a lie: nothing internal went wrong, the request was malformed. Fixed in two places rather than forty handlers — [`http/pgErrors.ts`](apps/api/src/http/pgErrors.ts) maps the caller-provokable SQLSTATEs (`22P02`/`22003`/`22007`/`22008` → 422, `23505` → 409, `23503`/`23502`/`23514` → 422) while still logging every one, and [`uuidParam`](apps/api/src/http/params.ts) rejects at the edge with a 404 so a malformed id and someone else's id give the same answer. Genuine faults (`42P08`, `08006`, `53300`) stay 500s on purpose. 11 unit tests pin the mapping; `verify:e2e` asserts 8 routes never 500.

  - **Proposing is free; approving is gated.** The Crew plan has no features and exists so a subcontractor can work for nothing (§5B) — gating proposals on the proposer's plan would mean a free subcontractor could never ask for a raise. `rate_cards` is resolved on the **hiring** company instead, which is whose cards approval writes. The mirror of the portal rule already in force, with the sides swapped.
  - **Immutability is the database's rule, not the route's.** A trigger allows an `UPDATE` on a locked card to touch `effective_to`/`active`/`updated_*` and nothing else, and refuses `DELETE` outright — so a later `PATCH` path added in good faith cannot quietly rewrite an agreed rate. The route refuses first with an explanation, because a trigger violation reaches a caller as a 500.
  - **Submission freezes the payload, for both sides.** The reviewer has no edit path at all; its only lever is reject-with-a-reason, and a rejection without one is a 422. A corrected schedule is a successor row carrying `predecessor_proposal_id`, never an edit.
  - **A draft is deleted, a submitted schedule is withdrawn.** Different verbs because they have different audiences: nobody has seen a draft, so there is nothing to explain; a submitted schedule sits in someone else's queue, so pulling it back leaves a terminal row. This is why no state but `DRAFT` has a null `submitted_at`, and the DB check says so.
  - **Retroactive activation is refused by default** and needs an `OWNER` plus a reason on the record. Approved time keeps its PAY snapshot frozen at submit (§6), so a back-dated rate disagrees with money already owed. Asserted both ways: a manager gets 403, an owner without a reason gets 422, and an owner with one gets the reason stored.
  - **One open negotiation per edge** (partial unique index on `DRAFT|SUBMITTED`). Two open proposals would make "what are we arguing about" ambiguous, and whichever approved second would silently win.
  - **Currency is carried but unlike currency is refused.** The agreement records its own unit so the money-boundary bullet below is a change of behaviour rather than a migration; until then §3.3's rule holds and the refusal names the FX snapshot that is missing.
  - **Payment terms and the PO ceiling are enforced, not recorded.** Terms default a new invoice's `due_at`; the ceiling is checked at **issue** — the point the amount becomes a claim on the PO — under an advisory lock so two invoices cannot each read a committed total that excludes the other. `DRAFT` and `VOID` are excluded from the committed figure on purpose.
  - **Engagement acceptance closes a real hole.** `POST /v1/engagements` used to create an `ACTIVE` edge, so a hiring company could bind another company to a commercial relationship it had never agreed to. It now lands `PENDING` and the provider accepts or declines — which is what the placeholder/invite path already did, so the two paths agree instead of contradicting each other.
  - **Assignment acceptance deliberately does *not* gate work capture.** Gating it would stop a crew logging hours they had already worked, hours after a decision taken by a different company, with the repair sitting in a third place. It is recorded and surfaced; whether it becomes a hard gate is left as an explicit later decision rather than smuggled in here. Proven: a time log is accepted while the assignment is still `PENDING`.
  - **`accepted_at` means accepted.** A declined assignment has none — `updated_at` and the audit row carry when a decline happened.   **The rules worth restating, because they are decisions rather than implementation:**
  - **An instant is a point in time; a date is a human's answer to "which day was that".** The product already stored both correctly — `timestamptz` for instants, `date` for days, with `work_date` asserted by the person who did the work rather than derived from when they pressed the button. East of UTC (Manila, +8) between local midnight and 08:00 the server is still on yesterday, so a genuinely back-dated schedule passed as current: **the safeguard silently off for a third of every day.** West of UTC (Los Angeles, −8) after 16:00 local the server is already on tomorrow, so a rate starting *today* was judged retroactive — a manager got a 403 and an owner was made to justify a schedule starting that morning. One line, both directions, invisible without a customer outside UTC.
  - **The hiring company's zone is the right one**, because it is whose `rate_cards` the approval writes and whose money the schedule governs — the same "resolve on the hiring side" rule the rest of the commercial module already follows.
  - **Changing a zone moves nothing.** Presentation and future bucketing only; no stored instant and no stored date. There is deliberately no backfill in 0015 for exactly that reason, and the e2e asserts stored rows are identical across a zone change.
  - **Null on a project means inherit, not unset.** A project that copied the company zone at creation would silently stop tracking it, and "wherever the business is" is the far more common intent than "wherever it was the day I made this project".
  - **Zones are validated against a real IANA list at both ends** — `Intl` in the app, `pg_timezone_names` in the database. A regex accepts `Not/AZone`, which then throws inside a business transaction; the DB constraint means a route that ever forgets to validate still cannot store a broken zone.
  - **A zone lookup never fails a business operation.** Every conversion falls back to UTC and logs. Refusing an approval over a zone string is worse than reporting it against a slightly wrong day — the wrong day is visible, the refusal looks like a bug in something else.
  - **DST is resolved, not thrown.** A spring-forward gap resolves *forward* (02:30 on a day that jumps 02:00 to 03:00 becomes 03:30, not 01:30 — resolving backward would silently move work an hour earlier than recorded); an autumn overlap takes the earlier of the two. Day ranges are computed from the next local midnight rather than by adding 24 hours, because a DST day is 23 or 25 hours and a fixed day would drop or double an hour of work twice a year.

    **The rules worth restating, because they are decisions rather than implementation:**
    - **The limiter must not become the attack.** Keying only on the email address hands anybody a lockout button for anybody else's account. Both budgets are counted and the **source budget is deliberately tighter than the identity budget**, so a single attacker is stopped by their own volume long before their victim's address is exhausted. The residual — a genuinely distributed attacker can still lock one address for one window — is not pretended away: it is why exhausting the identity budget emails the holder. A lockout somebody is told about is an incident; a silent one is a mystery.
    - **The refusal cannot be an oracle either.** A limiter that says "too many attempts for this account" is a *better* account-existence oracle than the endpoint it was added to protect. `rateLimitMessage` is one sentence and one number, and a unit test asserts the words `account`, `user`, `email`, `address`, `exists` and `password` never appear in it.
    - **One alert per lockout, and it falls out of the control flow rather than a flag.** The notification check is only reachable after a failure that passed the gate, so the first time it fires is the attempt that exhausted the budget and every later one is refused before reaching it.     - **Only failures consume budget, and successes are still recorded.** Counting successes would eventually lock out a busy office sharing one address — a support ticket that looks exactly like an attack and gets resolved by turning the limiter off. Successes are stored anyway so the ratio has a denominator: "logins are failing" and "nobody is logging in" are indistinguishable without one.
    - **The check runs before bcrypt, not after.** The point is to stop the server hashing tens of thousands of times for somebody with a word list; a limiter consulted after the comparison still burns the CPU it exists to protect.
    - **Nothing about the secret is stored, and the source is hashed.** No password, no length, no prefix — a rate-limit table that records anything about the value being guessed turns a nuisance breach into a serious one. The source is SHA-256'd with a server secret, because an unhashed column would be a log of which addresses signed in from where, which is the location history the packet's §7 refuses to build, and the IPv4 space is small enough to rainbow without the salt.
    - **`trust proxy` is a required deployment fact, not a default.** Too low and every request appears to come from the proxy, so one source budget is shared by the entire internet; too high and a caller forges a header to escape the budget. Acting on that signal needs a family, and `refresh_tokens` had no session and no predecessor column, so "the family" was not expressible. That, not rotation, was the work.

Ending *a token* is meaningless to the owner of a lost phone, because the token they signed in with was retired weeks ago. The extra exposure is real and named: a thief who replays within two minutes of the victim is not caught. ### Deferred to the end of Phase 6 — the payment system (owner decision, 2026-08-19)

**Paddle is the merchant of record (owner decision, 2026-08-20), and all payments are USD only.** Billing is
therefore moved to the *last* thing Phase 6 does, rather than the middle. This is
a sequencing decision, not a descoping one: the product still needs a way to take
money before launch.

Deferring it costs little, because nothing else in Phase 6 depends on it —
entitlements already resolve from `company_subscriptions` regardless of who wrote
the row, super admins can already set a plan, comp a trial and apply an override
from the Platform console, and `checkoutEnabled` already ships **off** with
§3.1.1(3)'s audited-admin arm carrying every additional company. The webhook inbox
the merchant integration will use is built and proven (0012). What a provider
decides is the *adapter* and the price table, not the shape of the system.

  - **Three primitives, because there are three different questions.** `clientId` answers *"have I already done this?"*; `expectedRevision` answers *"is what I am changing still what I read?"*; a tombstone answers *"is it gone, or am I not allowed?"* — two things a 404 says at once, and on an intermittent connection a timeout looks like both. All three are **opt-in per request**: a browser form submitted once by a person needs none of them, and requiring them would have made every existing caller a migration.
  - **The ledger stores the response, not the fact.** A ledger that only recorded "seen" would refuse the replay — and a refusal is not what a retrying client needs, since it has no other way to learn the id of the thing it just created. A replay returns byte-for-byte what the first attempt returned, so the client cannot tell which attempt it was, which is the whole definition of idempotent. A replay whose *body* differs is refused rather than answered: that is an id reused for a second act, and handing back the first answer would be a lost write dressed as a success.
  - **Two check-then-act races, both found by the acceptance script and neither by any unit test.** Written as two concurrent requests rather than two sequential ones, which is the only way either shows up. **(1)** Two simultaneous retries of one create both saw no receipt, both ran, and **two rooms existed where the client had asked for one** — fixed by claiming the id with `insert … on conflict do nothing returning` *before* the work, so the primary key is the arbiter and the loser waits for the winner's answer. **(2)** Two tabs composing against revision 4 both passed the revision check and both wrote, so **the second silently overwrote the first and nobody was told** — fixed by moving the comparison into the `update`'s own `where`, where the row lock makes it atomic.   - **A claim that fails is released, or the id is burned.** A create refused for a bad parent would otherwise leave an in-flight receipt, and the corrected retry would wait for an answer that is never coming. An in-flight row abandoned by a killed process is pruned on an hour's clock rather than seven days', for the same reason.
  - **The revision is the database's, through a trigger, not the route's.** A revision maintained by application code is correct until somebody adds the second write path, and the second write path is always added by whoever has not read the file. It deliberately does not fire when nothing changed: a no-op update that bumped the revision would invalidate every client's expected version over a change nobody made, which on a syncing device is a conflict prompt about nothing.
  - **A tombstone is disclosed only to somebody who could have read the live row**, and that rule is what keeps the whole idea from being a disclosure. Told carelessly it is an oracle — an outsider probing ids would learn which ones ever existed — so authorization runs first and unchanged, and everybody else still gets the 404 they would have got before tombstones existed. Asserted directly: an outsider's request for a tombstoned id and for an id that never existed are the same answer.
  - **410 for a write against a tombstone, 409 for a stale one**, because the client's next move differs: a queued edit for a deleted record should be abandoned, while a stale one should be re-composed against the record the 409 carries back with it.
  - **The ledger holds no customer prose.** It records the route *template* — the same rule the request log follows — and a SHA-256 of the request rather than the request, because a body is customer data and this table has no business holding a diary entry. Asserted on the stored row.

Bytes in the zip would stream gigabytes through an API whose storage design says bytes never pass through it, and would turn one bundle into a permanent unauthenticated copy of a project's entire evidence the moment somebody forwarded it.
  - The manifest must say this in prose, the way it already explains withheld columns — *"where are my photos"* is the first question a careful reader will have, and an unexplained absence reads as a bug or as evasion.

### ✅ Answered 2026-08-31 — the local stack, and where data is allowed to live

- [x] **All data is local until CrewQuo is production ready.** No hosted database holds customer-shaped rows, and none is to be created yet. Three things follow, each of which somebody could otherwise undo in good faith:
  - **[render.yaml](render.yaml) is a blueprint for later and is deliberately not applied.** It declares *paid* plans since the 2026-08-20 recovery decision, so applying it provisions real infrastructure — it records what production will be, it is not an instruction to build it now.
  - **The GitHub Actions schedule stays paused, and now by decision rather than by incident.** It is the only thing in the repo that runs against a remote `DATABASE_URL`, so switching it on *is* the act of standing up the hosted database this defers. The passes run by hand against the local stack instead. This supersedes the "provision the paid instance and repoint the secret" instruction recorded under §14 step 1 earlier the same day.
  - **Postgres keeps its data in a local Docker volume** (`crewquo_pgdata`) and nothing replicates it anywhere. Which also means it has exactly the durability of one laptop, and that is accepted for pre-production data — the §13.4 recovery promise is about production, and remains step 4 and unstarted.
- [x] **The API runs in Docker; the web app runs on the host.** `apps/api/Dockerfile` plus an `api` service in [infra/docker-compose.yml](infra/docker-compose.yml), so the stack that holds data is one `docker compose up` rather than a container plus a host process plus whichever `.env` that shell happened to read.
  - **The web app was deliberately left out.** Next.js hot reload through a Windows bind mount is markedly slower in a container, and — the deciding half — the web app stores nothing. Postgres is the only thing in this stack that holds anything, so containerising the web app would cost the dev loop and buy no data locality.
  - **Source is bind-mounted; `node_modules` never is.** The image installs its own for Linux, and mounting a Windows pnpm tree over it replaces a working symlink farm with paths that do not exist in the container. The local container deliberately consumes `@crewquo/shared` as source through `tsx`, so there is no local-image build artifact to fall out of step — which is why the mounts are `src` directories. Production separately emits `dist` with the shared source bundled.
  - **`--frozen-lockfile` inside the image required copying all five workspace manifests, not the two it runs.** The check validates the lockfile against the workspace it can see, and a workspace missing three of its projects is one the lockfile does not describe. Installing web's and mobile's dependencies is the price of running the same frozen check CI runs.
  - **An empty string is not an absent value, and it cost a boot failure to notice.** The first version passed optional keys through as `SENTRY_DSN: ${SENTRY_DSN:-}`, which *sets* the variable to `''`. `env.ts` types it `z.string().url().optional()`, where `.optional()` tolerates absent and `.url()` rejects empty — so the API refused to start over a key nobody had configured, and `NOTIFICATION_FROM_EMAIL` (`.email().optional()`) was one unset key from the same crash. `env_file` passes through what the file has and omits what it does not, which is the distinction the schema is drawing.
- [x] **The web app always runs on port 3000, and should be left running.** `next dev` treats `-p 3000` as a *preference*: with the port taken it prints one warning and moves to 3001, leaving an app that loads at the wrong address — the worst shape a misconfiguration takes, because everything that breaks does so somewhere else. The API's CORS allowlist is built from `APP_BASE_URL`, every link in an outbound email is written against that origin, and Playwright's `baseURL` is 3000 with `reuseExistingServer`, so a drifted port means a suite quietly driving a different server. `predev`/`prestart` now run [require-port-3000.mjs](apps/web/scripts/require-port-3000.mjs), which refuses to start and names what holds the port; both scripts also pass `-H 127.0.0.1`, loopback-only while data is local and immune to the IPv6 shadowing already documented for Postgres.
- [x] **The quiet-hours race is pinned, not merely re-run (2026-08-31).** The `PUT` that stored two nulls was the form reading React render state rather than the controls being submitted. Input state updates are asynchronous; if both input events and submit arrive in one browser task — the timing boundary session churn made intermittent — the fields can visibly hold `22:00` / `07:00` while the submit closure still sees the preceding empty state. `save` now reads `FormData` from the submit event, which is the browser's definition of what was submitted, and the browser case deliberately delivers those three events in one task so the old implementation fails deterministically. A half-entered window is now refused on-screen rather than silently translated into "clear both". The full **43-case serial parity story** is green with the pinned event order.
- [x] **One deliberate exception to data locality, recorded rather than buried: mail really sends.** `RESEND_API_KEY` stays live in `.env` (owner, 2026-08-31), so recipient addresses and notification bodies do leave the machine. Chosen knowingly, because a mail path nobody has watched deliver is a mail path nobody has tested. Unsetting the key makes the adapter record `SKIPPED` with a reason and send nothing, which is the switch if that trade stops being worth it.
